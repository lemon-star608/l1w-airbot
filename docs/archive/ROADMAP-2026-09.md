## 目标

一个跑在 L1-W 机载电脑上的 Python 程序,用 PICO 4 Ultra 的两个手柄分别遥操作
机器狗和 AIRBOT 机械臂,全程通过两套 SDK 的原生控制接口,并保证安全不变量。

```text
PICO 4 Ultra 手柄
  |  官方 App + PC-Service(现成)
  v
我们的 Python 程序(机载)
  |-- 手柄新鲜度检查
  |-- clutch:手位姿 -> 臂末端目标
  |-- 限幅 + 速率限制
  |-- 仲裁:分时策略
  |-- arming 状态机
  |-- 狗:UDP + JSON -> SetRemote 等价轴值
  `-- 臂:gRPC servo 流 + PTP 离散命令
```

只做运控,不接相机。演示形态是分时操作:开过去 -> 停 -> 操作臂。

**我们不写通信层。** 三个接口都是现成的:手柄是进程内 pybind 调用,狗是文档化的
UDP+JSON,臂是官方 gRPC 客户端。项目全部是 Python,除了在机载上编一次 pybind
模块之外没有编译步骤。

代码规模预计 1500–2500 行含测试。真正的工作量在安全逻辑、坐标系换算和时序,
不在搭管道。

## 架构

一个循环,50–100 Hz,每圈五步:

| 步 | 做什么 |
|---|---|
| 1 看 | 读两个手柄的位姿、grip/trigger 模拟量、按键、时间戳 |
| 2 信不信 | 新鲜度检查 + deadman 判定 |
| 3 算 | clutch 增量 -> 臂目标位姿;摇杆 -> 狗速度轴 |
| 4 限 | 限幅、速率限制、仲裁策略 |
| 5 发 | 狗发 JSON,臂发 gRPC |

**第 5 步永远执行。** 第 2 步判定不可信时跳过 3、4,直接发安全值。
本项目的核心语义:"停止"不是"不做事",是"持续做一件安全的事"。

## 拓扑与部署

全部跑在机载电脑,Mac 只做 SSH 启动和看日志,不在数据链路里。

```text
   Mac                    L1-W 机载电脑                      PICO 4 Ultra
    │                    (aarch64 Ubuntu 22.04)                (头显)
    │                                                            │
    └── SSH ──────────►  ① PC-Service (无头)  ◄──── Wi-Fi ───────┘
      启动/看日志           ↕ 进程内 pybind         狗自建热点
      不在数据链路          ② airbot-arm 服务       192.168.234.1
                           ③ 我们的 Python 程序
                              ├─► 狗:UDP 8081/8080(本机)
                              └─► 臂:gRPC 50051(本机)
```

机载上三个进程。跨 Wi-Fi 的只有头显那一跳,狗和臂都是本机链路。

启动顺序:

```bash
# Mac 上 ssh 进机载
tmux new -s teleop
/opt/apps/roboticsservice/runService.sh          # ① PC-Service
# ② airbot-arm 服务(装 deb 后按其方式启动)
python -m l1w_teleop                             # ③ 默认 dry-run
# 头显打开 XRoboToolkit App,指向 192.168.234.1
```

**必须 tmux 或 systemd。** 直接在 ssh 里跑,合笔记本时 SIGHUP 会打死程序。
按安全设计狗会零速、臂会保持,所以不危险,但演示会中断。

## 固定安全原则

1. **默认不运动。** 三级放行,默认最保守:

   | 级别 | 行为 |
   |---|---|
   | 默认 | 连接、读状态、打印将要发的命令;不请求控制权,不发运动命令 |
   | `--acquire-control` | 请求两边控制权,只发零速/保持 —— 单独验证 arming 路径 |
   | `--enable-motion` | 全开 |

2. **只用 SDK 原生控制接口。** 狗用 `remote` 消息(等价 `SetRemote`),臂用
   `move_end_pose`。不碰狗的 `lowlevel.h` 关节接口 —— 那等于自己写轮足平衡控制器。

3. **狗的安全态 = 持续发零速。** 不是停止发包(可能保持上一个速度),
   **绝不是 `CMD_EMERGENCY_STOP`** —— 那个让狗完全趴下,臂会跟着砸向地面。
   狗的"安全"是站着不动。

4. **臂的安全态 = 保持当前位姿。** 服务端有指令陈旧 watchdog,停发后以最后指令
   状态停住。**禁止进入重力补偿模式** —— 臂会变软,在会晃的底盘上等于让臂甩动。

5. **deadman 用 grip 模拟量。** `grip > 1.0 - 死区` 才算按下。左 grip 管狗,
   右 grip 管臂 clutch。松开立即进对应的安全态。

6. **新鲜度检查是第一条保护。** 官方 pybind 没有手柄 liveness API。两个判据叠加,
   任一命中等价 deadman 释放:时间戳不前进;位姿逐比特恒同(真实追踪永远有抖动)。

7. **watchdog 基于本机 `time.monotonic()`。** 不用头显时间判断超时。

8. **所有轴限幅 + 速率限制。** 狗轴先夹到 `[-1,1]` 再乘低速系数;臂目标位姿做
   速率限制,并叠加服务端 `set_arm_speed` 钳位作为第二道防线。非法浮点按 0 处理。

9. **退出即安全。** 正常退出、SIGINT/SIGTERM、异常、主循环结束,都必须走清理路径:
   狗发零速,臂 release 控制权。

10. **实体运动必须现场确认。** 任何会让机器人运动的步骤,执行前必须显式标注
    "这一步会让机器人运动",并由用户确认现场安全条件。

11. **夹爪在 deadman 释放时保持。** 不张开(掉负载),不加紧。

12. **v1 分时策略。** 右 grip 按下时狗强制零速;左 grip 按下且右 grip 松时狗可动、
    臂保持;都松则都在安全态。模式从 grip 状态自然涌现,无模式切换键。

## 输入映射

```text
左手 -> 狗                    右手 -> 臂
  axis Y  -> forward            pose      -> 末端目标(经 clutch)
  axis X  -> yaw                grip      -> clutch,按住才跟随
  grip    -> deadman            trigger   -> 夹爪开合(模拟量)
                                A / B     -> 离散命令,走 PTP 通道
```

`lateral` v1 暂不做。轮足横移大概靠腿实现,可能很慢或不稳,待实测后再决定放
右 axis X 还是不要。

离散命令(回收纳位、回零、去预备位姿)**不进高频流**。它们走
`planning_control` + PTP,是一次性、危险、不能丢也不能重复执行的操作,需要
显式确认。切换控制器有 50 ms sleep,必须停流后做:停流 -> 切 planning ->
执行 -> 切回 servo -> 恢复流。

## 组件

```text

clutch.py         手位姿 -> 臂目标位姿(坐标系换算)

dog_adapter.py    -> joystick 轴值
arm_adapter.py    -> servo 流 + PTP 离散命令两通道
safety.py         限幅、速率限制、双子系统 watchdog、安全态
arbiter.py        分时策略(可换)
state_machine.py  arming 时序
main.py           主循环
mocks/            假手柄、假狗、假臂
tests/            安全不变量测试
```

## 关键设计决定

**臂目标表达在机身坐标系。** 不用世界系。世界系需要靠 `odom_info` 反向补偿底盘
运动,而轮足的偏航里程计会漂,臂会跟着慢慢飘。机身系下底盘动时臂跟着动、
相对机身不动,符合直觉,且不吃里程计误差。

**clutch 三步。** 按下记基准(手位姿 + 臂末端当前位姿);增量叠加到基准;
松开时把目标重置到臂**实际**位姿(不是我们算的目标)。第三步保证下次接入
零跳变 —— 臂可能因限位或碰撞没走到位,不重置会有突跳。

**指令与实际的偏差监控。** 实际跟不上指令超过阈值,说明臂卡住或撞上了,
应停止,不能继续加大偏差硬顶。

**狗心跳独立线程。** 协议要求 50 ms 心跳、5 s 超时。不能被慢的 gRPC 调用饿死。

**臂控制权用短租约。** 默认 15 s 租约 / 5 s 续租。调短(如 3 s / 1 s)让进程被
kill -9 后的失控窗口更小。租约过期后控制权自动掉,不会留"没人管但仍有控制权"的臂。

**废掉 `auto_acquire`。** `arm_sdk` 的 `@requires_control(auto_acquire=True)`
装饰器会在我们主动 release 后,因一次误调运动函数而**静默抢回控制权并执行**。
封装层必须禁用,只允许显式获取。

**arm 之前先跟服务端对齐控制器模式。** `move_end_pose` 在四种模式下构造完全不同的
请求,而 `_current_controller` 只是客户端缓存。必须调 `GetController` 核对,不信缓存。

**`options.blocking = False`。** 流式喂 setpoint 不能阻塞等运动完成。

**发送路径不依赖接收解析。** watchdog 走本机时钟,"安全"就是发零速。狗的状态解析
错了,丢的是遥测不是安全。所以接收侧按需实现:连接状态、电量、故障、俯仰/侧倾、
控制模式、实测速度即可,其余 30 个 getter 不用。

## 现有 C++ 代码的处置

- **`status_monitor` 保留。** 它是 P2 验证 Python 协议解析的 ground truth,有独立价值。
  注意它和我们的接收端都绑 8080,**不能同时跑**。
- **`CommandSafetyGate` / `MockDogController` / `test_safety`** 的测试用例
  (deadman、watchdog 边界、限幅、显式 stop)移植成 Python 测试,确认新实现全过后
  删除 C++ 版本。它只有单子系统语义,双子系统不对称要重写;维护两套实现比删掉更糟。

## 分期

每一期严格比上一期多一样硬件。前两期完全不会让机器人运动。

### P0 全离线:三个假服务 + 全部安全逻辑

硬件:无。

三个 mock 不是测试便利,是主开发环境:

- **假手柄** —— mock 掉 `xrt.get_*`,能注入冻结位姿、时间戳停滞、grip 抖动
- **假狗** —— 绑 8080/8081 的 UDP server,收 JSON 回假状态,能注入丢包和故障
- **假臂** —— 用 `fsm_service_pb2_grpc.py` 现成 stub 起假 gRPC 服务,模拟租约续期
  和 servo 陈旧 watchdog

任务:

1. 三个 mock。
2. `xr_input` + 新鲜度检查(两个判据)。
3. `clutch` 坐标系换算和三步逻辑。
4. `dog_client`(UDP+JSON、心跳线程、状态解析)+ `dog_adapter`。
5. `arm_adapter`(servo 流 + PTP 两通道)。
6. `safety`(限幅、速率限制、双子系统 watchdog)。
7. `arbiter` 分时策略 + `state_machine` arming 时序。
8. `main` 主循环 + 三级放行开关。
9. 移植 C++ `test_safety` 的用例,并补双子系统不对称的测试。

**假臂必须写成"假设参数化"。** 臂的陈旧 watchdog 语义是从服务端二进制字符串反推的
(见下方未验证假设)。如果推错了,P0 测过的东西在真臂上是另一回事。假设要集中在
一处、可一行改掉,且计划里有显式的"验证 mock 假设"步骤(P3 任务 1)。

退出条件:

- 全部测试通过,覆盖:deadman 释放、watchdog 超时、位姿冻结、时间戳停滞、
  限幅、速率限制、仲裁互斥、arming 失败/超时、四条退出路径。
- 主循环对着三个 mock 稳定跑 50 Hz,每个安全决策都有日志。
- 代码里不存在绕过安全门直达 SDK 的路径。

### P1 真手柄 + 假狗假臂

硬件:PICO 4 Ultra + 一台电脑。**零风险,没有机器人会动。**

这一期解掉最大的未知,所以排在真机之前。

任务:

1. 装 PC-Service(headless deb),编 pybind 模块,跑通 `import xrobotoolkit_sdk`。
2. **确认 `get_time_stamp_ns()` 的语义** —— 是"最后收到数据的时刻"(能用)还是
   "查询时的本机时钟"(没用)。摘下头显、让手柄休眠、走出追踪范围,看读数变化。
3. 如果时间戳没用,验证位姿比特恒同判据是否足够;都不行则给 pybind 加
   `PXREADeviceConnect` / `PXREADeviceMissing` 回调(SDK 有,只是没暴露到 Python)。
4. 测真实数据率、抖动、gRPC 往返延迟(`time_delay_test` RPC 现成)。
5. **调 clutch 的 scale 和死区** —— 必须用真手真动作调,凭空猜不出来。
6. 确认头显系到机身系的旋转 —— 操作员站在狗旁边,朝向关系要实测。

退出条件:

- 真手柄驱动假狗假臂稳定运行。
- 新鲜度检查在真实断连场景下确实触发(至少覆盖:摘下头显、手柄休眠、手背到身后)。
- clutch 手感可用,接入无跳变,松开无突跳。

一个待确认项:PC-Service 能否在开发机上跑。我们只下了 arm64 deb,amd64 的没下;
且开发机是 Ubuntu 20.04 而 deb 是给 22.04/24.04 的,glibc 可能不兼容。
退路是 PC-Service 和我们的程序都在机载上跑(反正手柄数据是进程内读的,
两者必须同机),开发机只做编辑。

### P2 真狗 + 假臂

硬件:狗。**任务 4 起会让狗运动,逐项现场确认。**

前置:确认狗当前没有 `CM_EMERGENCY_STOP` 和 controller-link fault
(旧路线图记录过这两个故障)。

任务:

1. 跑 `status_monitor` 确认 SDK 层通,记下各状态值作为 ground truth。
2. **停掉 `status_monitor`**(端口 8080 冲突),跑我们的 Python 客户端读同样状态,
   逐项对数值,验证 JSON 解析正确。
3. **确认 `role` 字段取值和控制权确认时序** —— 协议文档里 roles 表写 `sdk`,
   但 `remote` 消息示例用 `"role": "remote"`。发 `CMD_SDK_CONTROL_RIGHT` 后
   等 `feedback` 里 `control_mode` 变化才算拿到,测出实际延迟。
4. `--acquire-control`:拿控制权,只发零速。确认狗不动、模式反馈正确、
   **官方手持遥控器能夺回控制权**。
5. `--enable-motion`,forward 从 0.05 归一化输入开始。
6. 单独验 yaw,再组合 forward + yaw。
7. 运动中释放 deadman;运动中让头显断连;运动中 kill 进程。三者都必须零速停下。

初始低速系数(保守软件初值,不是已标定物理速度):

```text
forward_scale = 0.20
yaw_scale     = 0.25
lateral_scale = 0.15   # v1 不用
```

退出条件:

- Python 状态解析与 `status_monitor` 一致。
- 手柄遥操作狗低速可控,运动可预测。
- deadman、watchdog、头显断连、进程退出、遥控器仲裁全部按预期停止。
- 日志能解释每一次运动。

### P3 真臂 + 真狗

硬件:臂,且 **CAN 链路已通**。这一期是硬阻塞项,见下方风险。

任务:

1. **验证 mock 假设** —— 这是所有臂上机操作的前置。臂如能拆下单独上台就单独做:
   发几个 servo setpoint,停发,观察是否以最后状态保持;测 `timeout_ms` 是否为
   陈旧窗口(设 200 ms 与 1000 ms 对比);kill -9 客户端观察租约过期行为;
   如能触发,观察 `smoothHalt failed` 分支的后果。结果回填到假臂,重跑 P0 测试。
2. `--acquire-control`:拿控制权,只发当前位姿(等价保持),确认臂不动。
3. 小幅 servo 跟随,scale 调到很小,只动单轴。
4. 完整 6 DoF clutch 跟随,验证接入/松开无跳变。
5. 夹爪开合,验证 `eef_eff` 力限和 deadman 释放时保持。
6. PTP 离散命令:回收纳位、回零,验证停流→切模式→执行→切回的时序。
7. 偏差监控:故意挡住臂,确认超阈值后停止而不是硬顶。
8. 耦合:装到狗上,验证分时策略 —— 右 grip 按下时狗确实零速。
9. 故障传播:狗故障时臂冻结;臂故障时狗零速。

退出条件:

- 臂 clutch 跟随可用,所有停止路径按预期。
- 分时互斥经过验证,单侧故障不导致另一侧失控。
- 假臂的假设已被真机确认或修正。

### P4 演示加固

硬件:全套。

1. systemd unit 或 tmux 启动脚本,一条命令起三个进程。
2. 状态机显式化 + 日志滚动保存(命令日志和故障日志分开)。
3. 计数器:数据率、新鲜度失败次数、watchdog 触发、arming 失败、偏差超限。
4. 崩溃或重启后进入 not-armed 状态,不因开机自动允许运动。
5. 演练故障:拔头显、杀 PC-Service、杀 airbot-arm、断 CAN、狗报故障。
6. 写清部署、启动、现场停机流程。

退出条件:

- 任一组件失败都有已测试的安全结果。
- 演示流程可重复,冷启动到手柄接管有明确步骤。

## 未验证的假设

这些结论来自读代码、读文档和反编译字符串,**不是实机验证过的**。每一条都标了
验证归属期。写代码时要让它们集中、可一行改掉。

| 假设 | 来源 | 验证 |
|---|---|---|
| 臂 servo 模式有服务端指令陈旧 watchdog,超时以最后指令状态保持 | `airbot-arm` 二进制字符串:`Command is stale, halting servo with last commanded state` | P3.1 |
| `move_end_pose(timeout_ms=)` 就是那个陈旧窗口 | 它被塞进 request proto 发给服务端,不是 gRPC deadline | P3.1 |
| `get_time_stamp_ns()` 是"最后收到数据的时刻" | 未知,也可能是查询时的本机时钟 | P1.2 |
| 位姿逐比特恒同可作为冻结判据 | 真实追踪应有抖动,未在真手柄上确认 | P1.3 |
| 狗 `remote` 消息的 `role` 填 `remote` | 协议文档示例如此,但 roles 表写 `sdk` 是程序化控制的 role | P2.3 |
| 狗发送侧 JSON 格式与文档一致 | 文档完整,但短 key 未在 `libzsibot.a` 的字符串里独立出现 | P2.2 |
| PC-Service 和我们的程序必须同机 | 手柄数据是进程内 pybind 调用,推断如此 | P1.1 |

`smoothHalt failed` 那条失败分支的后果**完全未知**,是危险分支。P3.1 如能触发就观察。

## 已知风险

**硬阻塞:臂的 USB-CAN / `slcan.ko`。** CAN 不通,`airbot-arm` 服务连不上电机,
P3 无论代码多好都做不了。狗那条线(P0–P2)不受影响,可以先走完。
这项修复由并行工作流负责,本路线图归档时不修改当时的 `kernel/`、slcan
安装脚本和 slcan 模块说明。

**狗的平衡控制器是黑盒。** 我们不知道它怎么处理臂带来的变化负载分布。如果臂在狗上
不是官方支持的配置(自己搭的支架),我们就在它的设计包线外面。这是 v1 采用分时策略
而不是同时运动的主要理由 —— 分时下臂动时狗静止,重心变化不叠加动态扰动。

**同时运动往后放。** 想放开的话要加三条交叉限制(臂伸展限狗速、俯仰/侧倾冻臂、
带臂转向限 yaw 速率),常数只能实机试,试的过程本身有风险。仲裁器保持成可换策略的
组件,不改架构就能加。另外行进中做精细操作物理上拿不到精度 —— 轮足步态起伏会让
夹爪在世界系里晃,即使臂完美跟踪机身系目标。

**版本不一致。** 臂客户端 `arm_sdk` 5.2.3 vs 服务端 deb 5.2.5;PC-Service 的 deb
里二进制是 2025-04-29 编的,而源码有到 2025-10-23 的提交。装机时要对齐,
遇到"README 描述了但实际没有"的行为要想到这一点。

**机载算力未验证。** 机载上要同时跑 PC-Service、airbot-arm(算 IK)和我们的
50–100 Hz 循环。另外 `airbot-arm` 是否在机载 aarch64 上跑过尚不清楚 —— 如果一直在
笔记本上跑,这本身是个待验证项,应在 P3 之前单独确认。

**SDK 只提供二进制库,内部缺陷无法修补。** 狗 SDK 的 C++ 构造函数在机器人无响应时
会永久阻塞且 Ctrl+C 打不断 —— 这是我们狗侧走裸 UDP 而不是包 `libzsibot.a` 的
理由之一,裸 socket 没有这个失效模式。

**局域网无认证无加密。** 只能用于受控测试网络。公网或不可信局域网禁止开启 motion。

**狗曾报 `CM_EMERGENCY_STOP` 和 controller-link fault。** P2 开始前必须重新确认。
